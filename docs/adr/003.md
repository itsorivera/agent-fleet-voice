## ADR 003: Appointment Scheduling Assistant for a Dental Center

### Status
**Accepted**

### Context
A medium-sized dental clinic needs to automate inbound phone calls to book, reschedule, and cancel appointments, as well as answer basic inquiries regarding treatments and insurance coverage.
* **Key Non-Functional Constraints:**
* Must converse fluidly while querying real-time availability in the medical management system (HIS / EHR / Google Calendar).
* Calls to medical availability APIs can take between 800ms and 2.5 seconds. The bot cannot leave dead silence or freeze the call.
* Moderate operational and computing budget.

### Decision
Adopt the **GPT-Live** architecture (Real-time conversational session on the frontend/edge decoupled from the Business Logic and Scheduling Backend).

### Technical and Business Justification
1. **Decoupling Voice I/O from Business Latency:** This architecture allows the assistant to keep the voice interaction active (speaking natural filler phrases such as *"Give me just a second, I'm checking Dr. Perez's schedule for Thursday..."*) while an asynchronous backend thread executes queries against slow databases or booking systems.
2. **Reuse of Existing Backend Logic:** If the clinic already has a WhatsApp or web chatbot for scheduling, the GPT-Live architecture allows reusing the existing rules engine and backend without rewriting the booking logic to fit a monolithic Realtime API session.
3. **Graceful Conflict Handling:** If a scheduling collision occurs while booking a slot, the backend notifies the live conversational agent so it can negotiate an alternative with the patient without resetting the call.

### Discarded Alternatives
* **Pure Realtime API:** If the dental scheduling software API experiences latency spikes, direct tool calling in a pure session bottlenecks the model's fluency or may cause timeouts and inconsistent responses due to a lack of granular acoustic filler control.
* **Chained Voice Pipeline:** While technically feasible, it typically delivers a more rigid experience when scheduling dates (where schedule negotiation is often iterative and interrupted by the user: "Tuesday at 3... no, wait, 5 is better").

### Consequences
* **Positive:** Excellent balance between cost and user experience; tolerates latency fluctuations in legacy external systems; allows reuse of existing microservices.
* **Negative / Challenges:** Requires designing a robust event protocol (using SSE, WebSockets, or queues) between the voice orchestrator and the booking backend to synchronize state without causing dialogue drift.
