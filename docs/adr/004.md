
## ADR 004: VoiceLive Agent Mode vs. Foundry Voice Agents in a Live Voice Application

### Status
**Accepted**

### Context
The project needs to connect a real-time voice client to an agent hosted in Microsoft Foundry. Two paths exist that are easily confused because both use WebSockets, PCM16 audio, and the term "voice agent," but **they are not interchangeable**:

* **Path A — VoiceLive Agent Mode + `kind=prompt` agent.** The client opens `wss://<resource>.services.ai.azure.com/voice-live/realtime` with the parameters `agent-name` and `agent-project-name`. VoiceLive provides STT, orchestration, and TTS, invoking the *prompt* agent via the Responses API. The client configures the session using `session.update` (voice, VAD, echo cancellation, noise suppression, audio formats).
* **Path B — Foundry Voice Agents + `kind=voice` agent.** The client connects directly to the agent's real-time endpoint using `project.voice_agents.realtime.connect(agent_name=...)`. The agent owns the model (for example, `gpt-realtime-2.1`), instructions, greeting, voice, VAD, and audio pipeline. The client **does not** send `session.update`; it only streams audio and events.

**Constraint observed in this project (November 2026):** The agent `chat-agent` was created as `kind="voice"` (`sub_protocol="realtime"`, `model="gpt-realtime-2.1"`). When consumed via VoiceLive Agent Mode, the session establishes and transcription works, but the service returns empty responses:

```text
# VoiceLive Agent Mode with chat-agent (kind=voice)
response.created : ...
response.done    : status="completed", output=[], total_tokens=0

# VoiceLive Agent Mode with a prompt agent (kind=prompt)
response.output_audio_transcript.done : "Hello, how can I help you today?"
response.done    : status="completed", output=[audio message]
```

Furthermore, the agent's Responses endpoint explicitly rejects that kind:

```text
400 - Endpoint-scoped routes only support prompt and hosted agents.
      Agent kind 'voice' is not supported.
```

In other words: **VoiceLive Agent Mode only supports prompt agents; `kind=voice` agents must be consumed through their own real-time protocol.** The failure is silent (no `error` event is emitted), making it particularly costly to diagnose.

### Decision
Use **Foundry Voice Agents (`kind=voice`) as the default architecture for new live voice experiences**, reserving **VoiceLive Agent Mode with prompt agents** for reusing existing text agents or when fine-grained client-side audio control is required.

Specifically:
1. *Voice-first* applications (telephony, reception, conversational assistance) must be implemented using `project.voice_agents.realtime.connect(...)` with a `kind=voice` agent.
2. `kind=prompt` agents are exposed to voice exclusively through VoiceLive Agent Mode.
3. A `kind=voice` agent must **never** be configured in `AZURE_VOICELIVE_AGENT_ID`. If the same domain logic is required across text and voice, maintain two artifacts (prompt for text/VoiceLive and voice for real-time) powered by a shared definition of instructions and tools.

Reference repository artifacts:
* `reference/06-voice-live/Python/chat-client/chat-client.py` → Path A (VoiceLive, prompt agent).
* `reference/06-voice-live/Python/chat-client/text_client_voice.py` → Path B (Foundry Voice Agent, `kind=voice`).

### Technical and Business Justification
1. **Latency and Naturalness:** Path B is native *speech-to-speech*; it eliminates the STT → text → TTS step and preserves prosody, pauses, and interruptions (*barge-in*) with lower perceived latency. Path A chains three stages together, adding hundreds of milliseconds.
2. **Configuration Ownership:** In B, voice, VAD, echo cancellation, noise suppression, greeting, tools, and processing stages reside within the agent's versioned definition. This enables behavioral changes without redeploying the client and maintains channel parity (web, phone, Teams). In A, part of this configuration resides in client code (`session.update`), leading to drift across applications.
3. **Turnkey Telephony and Observability:** Foundry voice agents include built-in connectors for Twilio/Teams Phone, voice pipeline traces, stored conversations, and evaluation tooling. Replicating this in VoiceLive requires building custom plumbing.
4. **Text Asset Reuse:** If a tested prompt agent already exists (instructions, tools, knowledge), Path A exposes it via voice without rewriting. It represents the lowest-risk migration path for existing text agents.
5. **Fine Control and Compliance:** Path A allows inspecting and sanitizing text between STT and LLM, enforcing deterministic guardrails, and selecting audio formats or voices per session. It remains preferable in regulated domains where textual payload interception is required (see ADR 001).

### Decision Matrix

| Criterion | A: VoiceLive + `kind=prompt` | B: Voice Agents + `kind=voice` |
|---|---|---|
| Protocol | `/voice-live/realtime` + `agent-name` | Agent's real-time endpoint |
| Session config | Client (`session.update`) or agent metadata | Agent definition (server-side) |
| Model | That of the prompt agent (text) | Realtime or self-managed text |
| Latency | Medium (STT → LLM → TTS) | Low (speech-to-speech) |
| Prosody / barge-in | Good, with orchestration | Native |
| Telephony | Manual (ACS/Twilio) | Integrated |
| Traces / evaluation | Manual | Integrated |
| Text + voice same agent | Yes (same prompt agent) | No (voice agent does not accept text Responses) |
| PII interception between audio & LLM | Yes | Limited (managed pipeline) |
| Maturity | Legacy path; Microsoft recommends migration | Recommended path for new voice applications |

### Discarded Alternatives
* **Using `chat-agent` (`kind=voice`) from VoiceLive Agent Mode:** Discarded based on empirical evidence; produces `response.done` with `output=[]` and no audio, without an explicit error.
* **Using a `kind=voice` agent via the text Responses API:** Discarded by design; the service returns `Agent kind 'voice' is not supported`.
* **Converting `chat-agent` to `kind=prompt`:** Discarded because interaction mode cannot be altered after agent creation; it would require provisioning a new agent and forfeiting voice-specific configurations (real-time model, greeting, VAD, voice).
* **Reimplementing the STT/LLM/TTS pipeline manually:** Discarded due to high operational cost and the loss of integrated telemetry and telephony connectors.

### Consequences
* **Positive:** A single, unambiguous architecture for new voice workflows; lower latency; version-controlled agent configuration; bundled telephony and observability; eliminates the "connects but does not respond" failure mode.
* **Negative / Challenges:** Requires `azure-ai-projects[voice] >= 2.11.0` (project was on 2.3.0); client must migrate from `azure-ai-voicelive` to `voice_agents.realtime`; no direct dual-use of a prompt agent as a voice agent; certain features (telephony, sub-agents) require `allow_preview=True` or the header `Foundry-Features: VoiceAgents=V1Preview`; output audio arrives as 24 kHz mono PCM16 deltas that the client must play back or persist.
